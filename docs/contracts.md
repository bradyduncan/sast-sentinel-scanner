# Contracts

## DynamoDB: `jobs` table

**Table name:** `sast-sentinel-jobs`
**Billing mode:** `PAY_PER_REQUEST` (on-demand)
**TTL attribute:** `expires_at` (Unix epoch seconds; set ~30 days from `created_at`)

### Keys

| Key | Attribute | Type | Notes |
|---|---|---|---|
| Partition key | `job_id` | String (UUID) | Generated by `webhook-receiver` on receipt |
| Sort key | _(none)_ | — | One item per job |

### Global Secondary Index

| Index | PK | Projection | Purpose |
|---|---|---|---|
| `delivery-id-index` | `delivery_id` (String) | `KEYS_ONLY` | Webhook idempotency check — `webhook-receiver` queries this before kicking off Step Functions. Eventual consistency is acceptable given GitHub's retry cadence. |

### Attributes

| Attribute | Type | Written by | Notes |
|---|---|---|---|
| `job_id` | String | webhook-receiver | UUID, PK |
| `delivery_id` | String | webhook-receiver | `X-GitHub-Delivery` header, GSI PK |
| `status` | String | webhook-receiver, then each state | See [Job status enum](#job-status-enum) |
| `created_at` | String | webhook-receiver | ISO-8601 |
| `updated_at` | String | every writer | ISO-8601 |
| `expires_at` | Number | webhook-receiver | Unix epoch seconds (TTL) |
| `repo_owner` | String | webhook-receiver | e.g., `"anthropics"` |
| `repo_name` | String | webhook-receiver | e.g., `"claude-code"` |
| `pr_number` | Number | webhook-receiver | |
| `commit_sha` | String | webhook-receiver | Commit actually scanned (record what the PR head was at webhook time) |
| `installation_id` | Number | webhook-receiver | GitHub App installation ID — required by fetch-code and post-comment for auth |
| `s3_staging_prefix` | String | fetch-code | e.g., `"staging/<job_id>/"` |
| `s3_results_key` | String | fargate scanner | e.g., `"results/<job_id>/results.json"` |
| `execution_arn` | String | webhook-receiver | Step Functions execution ARN |
| `summary` | Map | fargate scanner | `{ high: N, medium: N, low: N }` |
| `error` | String | any writer on failure | Only present when `status = FAILED` |

### Access patterns covered

| # | Pattern | Operation |
|---|---|---|
| 1 | Idempotency check on incoming webhook | `Query` GSI `delivery-id-index` where `delivery_id = :d` |
| 2 | Read job by id (status, post-comment, fetch-code, scanner) | `GetItem` PK `job_id` |
| 3 | Update status / write results metadata | `UpdateItem` PK `job_id` |

Not currently supported (add GSI later if needed): "list all jobs for repo X", "list all FAILED jobs".

## Job status enum

`PENDING` → `FETCHING` → `SCANNING` → `COMMENTING` → `DONE` | `FAILED`

### State meaning

| Status | When | Meaning |
|---|---|---|
| `PENDING` | webhook just arrived | Job record exists, Step Functions has been kicked off, but no actual work has started |
| `FETCHING` | fetch-code Lambda is running | Authenticating to GitHub, downloading PR files, staging them to S3 |
| `SCANNING` | Fargate task is running | Scanner is reading from S3 and analyzing code |
| `COMMENTING` | post-comment Lambda is running | Reading results from S3, formatting markdown, calling GitHub API |
| `DONE` | terminal success | PR comment was posted. Pipeline complete. |
| `FAILED` | terminal failure | Something broke; the `error` attribute explains what. |

### Responsibility model

**Each component writes its own status on entry; each component writes terminal status on exit.** Step Functions only writes `FAILED` from its error-catch branch when a component crashes before it could write its own.

| Transition | Written by | When |
|---|---|---|
| _(no prior state)_ → `PENDING` | webhook-receiver | Initial `PutItem` when job is created |
| `PENDING` → `FETCHING` | fetch-code Lambda | First action after parsing input |
| `FETCHING` → `SCANNING` | scanner cli.js | First action after reading env vars |
| `SCANNING` → `COMMENTING` | post-comment Lambda | First action |
| `COMMENTING` → `DONE` | post-comment Lambda | After successful GitHub API response |
| _any_ → `FAILED` | the component that caught the error, OR Step Functions error branch if uncaught | Sets `error` attribute too |

### Rules

- **HIGH-severity findings do not change the status.** The SNS/email branch is a side effect from a Step Functions Choice state — the main flow still goes `SCANNING → COMMENTING → DONE`. Severity counts live in the `summary` attribute, not the status.
- **"Scan succeeded but comment failed" ends in `FAILED`.** No half-success state. The `error` attribute distinguishes which stage failed; scan results remain in S3 for manual recovery.
- **Duplicate webhook deliveries** (idempotency hit) do not create a new job or change any status. webhook-receiver returns 200 immediately.
- **Step Functions execution timeout** triggers the error catch branch → `FAILED` with `error: "execution timeout"`.

### State diagram

```
                  ┌──────────────────────────────────────────┐
                  │                                          ▼
webhook → PENDING → FETCHING → SCANNING → COMMENTING → DONE
              │         │          │           │
              └─────────┴──────────┴───────────┴──────► FAILED
                  (any stage can fail; error attribute set)
```

## S3 layout

Two buckets. IAM scopes each component to the minimum prefixes it needs.

### Staging bucket

```
staging/<job_id>/pr_files.tar.gz
```

- **Scope:** only files changed in the PR (not the full repo).
- **Contents:** a `tar.gz` archive whose entries preserve the repo-relative paths of changed files (e.g., `src/auth/login.js`, `lib/utils.js`).
- **Producer:** fetch-code Lambda. Calls `GET /repos/{owner}/{repo}/pulls/{pr}/files` to list changed files, fetches each at the PR head SHA, bundles them, and uploads.
- **Consumer:** Fargate scanner. Downloads the single object, extracts to `/tmp/<job_id>/`, runs `scanDirectory()` on the extracted root.
- **Lifecycle:** delete objects after 7 days (code is in GitHub anyway).
- **No other readers or writers.**

### Results bucket

```
results/<job_id>/results.json
```

- **Contents:** the full scanner output. See [Scanner output JSON](#scanner-output-json) for the exact shape.
- **Producer:** Fargate scanner (cli.js).
- **Consumer:** post-comment Lambda.
- **Lifecycle:** retain 90 days for debugging.
- **No other readers or writers.**

### Notes

- Bucket names are an infrastructure concern (Terraform), not part of this contract.
- Encryption at rest, versioning, and public-access-block are required on both buckets but configured in `infrastructure/envs/dev/s3.tf`.
- Because the scanner only ever sees PR-changed files, there is no need to filter findings by path at comment time — every finding is in-scope for the PR.

## Scanner output JSON

**Location:** `results/<job_id>/results.json` in the results bucket.
**Producer:** Fargate scanner (`sast/backend/cli.js`).
**Consumer:** post-comment Lambda.

Step Functions does **not** read this file. The severity check that branches to SNS reads `summary.high` directly from DynamoDB via the AWS SDK integration — the scanner writes `summary` to both DynamoDB and results.json.

### Shape

```json
{
  "schema_version": "1.0.0",
  "job_id": "9a1f4c8e-...",
  "scanner_version": "1.0.0",
  "scanned_at": "2026-05-21T18:42:11Z",
  "repo": { "owner": "anthropics", "name": "claude-code" },
  "pr_number": 42,
  "commit_sha": "abc1234...",
  "summary": {
    "total": 3,
    "high": 1,
    "medium": 1,
    "low": 1
  },
  "findings": [
    {
      "id": "SQL_INJECTION",
      "name": "SQL Injection",
      "severity": "HIGH",
      "description": "User input concatenated into SQL queries can lead to injection attacks.",
      "message": "String concatenation with request parameter in SQL query",
      "file": "src/db/users.js",
      "line": 42,
      "column": 18,
      "evidence": "const q = 'SELECT * FROM users WHERE id=' + req.params.id"
    }
  ]
}
```

### Top-level fields

| Field | Type | Notes |
|---|---|---|
| `schema_version` | String | Semver. Bump on any breaking change to this shape. |
| `job_id` | String | Matches DynamoDB PK. |
| `scanner_version` | String | From `sast/backend/package.json`. Useful for "why did this PR get different findings". |
| `scanned_at` | String | ISO-8601, set when cli.js starts scanning (not webhook receipt time). |
| `repo` | Object | `{ owner, name }`. |
| `pr_number` | Number | |
| `commit_sha` | String | The SHA actually scanned. |
| `summary` | Object | `{ total, high, medium, low }`. Duplicated to DynamoDB. |
| `findings` | Array | Sorted by severity DESC, then `line` ASC. Empty array on a clean scan. |

### Finding fields

| Field | Type | Notes |
|---|---|---|
| `id` | String | Rule ID, e.g., `SQL_INJECTION`. Stable identifier. |
| `name` | String | Human-readable name, e.g., `"SQL Injection"`. |
| `severity` | String | `HIGH` \| `MEDIUM` \| `LOW`. |
| `description` | String | General description of the rule. Same for every finding of this `id`. |
| `message` | String | Finding-specific message (e.g., what was matched). |
| `file` | String | Repo-relative path. |
| `line` | Number | 1-indexed. |
| `column` | Number | 1-indexed. |
| `evidence` | String | The matched line of code (single line). |

### Conventions

- **Field naming:** `snake_case` throughout (matches DynamoDB attribute style).
- **Empty scan:** `findings: []` with `summary` zeroed out — file is still written so post-comment can post a clean-scan comment.
- **Scanner failure:** **do not** write a partial `results.json`. Job goes to `FAILED` in DynamoDB with `error` set; the file simply doesn't exist for that job. post-comment Lambda only runs on a successful scan (Step Functions branches on status).
- **Presentation is not the scanner's job.** No pre-formatted markdown, HTML, or rendered output in this file — only structured data. post-comment Lambda owns formatting.

## Step Functions state I/O

### Philosophy: thin state passing

Step Functions carries only the **execution context** — stable identifiers immutable for the lifetime of the execution. All mutable job state lives in DynamoDB; Lambdas and tasks read/write DynamoDB rather than accumulating state in Step Functions. This keeps execution payloads well under the 256 KB Step Functions limit and avoids drift with DynamoDB.

### Execution context (initial input)

webhook-receiver starts each execution with:

```json
{
  "job_id": "9a1f4c8e-...",
  "repo": { "owner": "anthropics", "name": "claude-code" },
  "pr_number": 42,
  "commit_sha": "abc1234...",
  "installation_id": 12345
}
```

Every state receives this. States use `ResultPath: null` to discard their own output, preserving the context.

### State machine layout

```
1. FetchCode            (Task: Lambda invoke)
2. RunScanner           (Task: ecs:runTask.sync)
3. ReadJobSummary       (Task: dynamodb:getItem)
4. HighSeverityCheck    (Choice)
       ├─ if high >= 1 → 5. NotifyHighSeverity → 6
       └─ else        → 6
6. PostComment          (Task: Lambda invoke)
7. Success              (Succeed)

Error catch on states 1, 2, 6:
   → HandleFailure       (Task: dynamodb:updateItem — status=FAILED, error=$.error.Cause)
   → PostFailureComment  (Task: Lambda invoke — same post-comment Lambda)
   → Fail                (Fail terminal)
```

### Per-state I/O

#### 1. FetchCode

- **Input:** execution context.
- **Action:** invokes fetch-code Lambda. Lambda fetches PR-changed files from GitHub, bundles as `pr_files.tar.gz`, uploads to staging bucket, writes `s3_staging_prefix` to DynamoDB.
- **ResultPath:** `null` — Lambda's return value is discarded.

#### 2. RunScanner

- **Input:** execution context.
- **Action:** `ecs:runTask.sync` (synchronous wait). Container overrides:
  ```json
  {
    "ContainerOverrides": [{
      "Name": "scanner",
      "Environment": [
        { "Name": "JOB_ID",         "Value.$": "$.job_id" },
        { "Name": "STAGING_BUCKET", "Value": "${staging_bucket_name}" },
        { "Name": "STAGING_KEY.$",  "States.Format('staging/{}/pr_files.tar.gz', $.job_id)" },
        { "Name": "RESULTS_BUCKET", "Value": "${results_bucket_name}" },
        { "Name": "RESULTS_KEY.$",  "States.Format('results/{}/results.json', $.job_id)" },
        { "Name": "JOBS_TABLE",     "Value": "${jobs_table_name}" }
      ]
    }]
  }
  ```
- Bucket and table names are injected from Terraform at state-machine-definition render time.
- Scanner writes `summary` and `s3_results_key` to DynamoDB on success.
- **ResultPath:** `null` — ECS task details discarded.

#### 3. ReadJobSummary

- **Action:** `dynamodb:getItem` with `Key: { job_id: { S: $.job_id } }`.
- **ResultPath:** `$.job` — item lands at `$.job.Item`. The `high` count is at `$.job.Item.summary.M.high.N` (string, per DynamoDB number-type encoding).

#### 4. HighSeverityCheck (Choice)

```json
{
  "Variable": "$.job.Item.summary.M.high.N",
  "NumericGreaterThanEqualsPath": null,
  "NumericGreaterThanEquals": 1,
  "Next": "NotifyHighSeverity"
}
```
Default → `PostComment`.

#### 5. NotifyHighSeverity

- **Action:** `sns:publish` to the HIGH-severity topic.
- **Message:** `States.Format('{}/{} PR #{} — {} HIGH severity findings. Job: {}', $.repo.owner, $.repo.name, $.pr_number, $.job.Item.summary.M.high.N, $.job_id)`
- **ResultPath:** `null`.
- **Next:** `PostComment` (comment always posts; SNS is a side effect).

#### 6. PostComment

- **Input:** execution context.
- **Action:** invokes post-comment Lambda.
- **Lambda behavior:** reads `status` from DynamoDB.
  - `COMMENTING` → reads `results.json` from S3, formats success comment.
  - `FAILED` (when called from the error path) → reads `error` from DynamoDB, formats failure comment.
- **ResultPath:** `null`.

#### Error catch (on FetchCode, RunScanner, PostComment)

```json
"Catch": [{
  "ErrorEquals": ["States.ALL"],
  "ResultPath": "$.error",
  "Next": "HandleFailure"
}]
```

#### HandleFailure

- **Action:** `dynamodb:updateItem` — sets `status = FAILED`, `error = $.error.Cause`, updates `updated_at`.
- **Next:** `PostFailureComment`.

#### PostFailureComment

- Invokes the **same** post-comment Lambda. It reads status from DynamoDB, sees `FAILED`, formats accordingly. No second Lambda needed.
- **Next:** `Fail` (terminal).

### Conventions

- **`ResultPath: null` everywhere** except `ReadJobSummary`. Keeps the execution context clean.
- **No fat state.** Findings, file paths, and other large payloads never enter Step Functions state — they live in S3/DynamoDB and are referenced by `job_id`.
- **Static configuration via Terraform.** Bucket names, table names, ARNs, topic ARNs are templated into the state machine definition at deploy time — not passed through state.
- **Synchronous task waits.** `ecs:runTask.sync` blocks until the Fargate task ends. Scans are expected to be sub-minute; if they ever exceed the per-state timeout, increase the timeout rather than switch to async/callback patterns.
